## 3. 商店／批量購買更新

### 已確認來源行為

- `buy.c` 支援 `buy 10 manto from waiter` 類型的數量購買，數量上限 100。
- 價格以單價乘購買數量計算。
- `vendor.c` 在確認商品時檢查庫存是否足夠，交貨時支援可堆疊物品、液體容器與多件非堆疊物品，並按數量扣庫存。
- `waiter.c` 將數量傳入延遲交貨流程，並用 `on_service` 防止同一店小二同時接單。

### 必須修正後才能宣稱交易安全

目前來源的 `buy.c` 在呼叫 `owner->deliver_merchandise(...)` 後就會扣款；`waiter.c` 則透過 `do_chat` 延遲交貨。如果顧客在交貨前離開房間，`handover()` 會直接返回，而原本 `buy.c` 已完成扣款。外層 `catch()` 只能攔截呼叫當下的同步錯誤，不能捕捉之後才發生的延遲交貨失敗。

因此：
- 批量購買來源已保存；
- **交貨成功與扣款原子性仍是 RUNTIME BLOCKED / NEEDS FIX**；
- 不得因為靜態測試通過就宣稱「交貨失敗不扣款」已驗收；
- 不可直接把 ES2M 的 `buy.c`、`vendor.c`、`waiter.c` 整檔覆蓋 Original ES2。

## 4. 戰鬥／武學成長更新

### 已確認來源行為

- `combatd.c` 的 `restored_dodge_gain()` 在成功閃躲流程中處理 combat 實戰經驗與 dodge 學習進度。
- `restored_parry_gain()` 在成功格擋流程中處理 combat 實戰經驗與 parry 學習進度。
- `restored_hit_gain()` 只在 `fight()` 判定 `damage > 0` 後呼叫。
- `basic_attack_skills` 列出基本武器／空手攻擊；只有非基本技能造成有效傷害時，才增加 `martial art` 造詣。
- 不應把普通木劍／基本攻擊命中當成武術造詣來源；也不可把「成功閃躲／格擋的 combat 成長」誤判成「每次命中都增加 combat」。

### 驗證邊界

這些是 ES2M 原始碼行為與靜態契約，不等同於 KING 遊戲內實戰 PASS。KING Runtime 仍須用 Neolith 實機驗證成功閃躲、成功格擋、普通攻擊命中與已啟用特殊武功有效命中四種情境。

## 5. Original ES2 保護與後續導入方式

- `es2m_snapshot/` 是 ES2M 證據快照，不是 Original ES2。
- 已存在的 Original Runtime 同名檔不得以整檔複製方式覆蓋。
- 後續以最小差異的 Runtime adapter（執行環境轉接層）導入；先修正延遲交貨付款問題，再測試庫存、金錢、負重／容器限制、玩家離開、存檔、退出與重新登入。
- 在有 Neolith Runtime 測試證據之前，商店交易與戰鬥成長不得標示為完整 Runtime PASS。
